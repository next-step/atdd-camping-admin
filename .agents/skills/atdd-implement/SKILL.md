# ATDD 최소 구현

실패하는 인수 테스트를 변경 기준으로 삼아 최소 구현하고, 왜 그 지점만 변경했는지 설명한다.

## 작업 전

1. 적용되는 저장소 지침과 대상 티켓의 범위를 확인한다.
2. 저장소에 있으면 `docs/principles.md`, `docs/plan.md`, 관련 `docs/acceptance-criteria.md`, `docs/test-guide.md`를 읽는다.
3. 대상 인수 테스트를 실행해 Red 상태를 재현한다. 테스트가 실패하지 않으면 구현을 시작하지 말고 기준과 테스트 상태를 보고한다.
4. Red를 남긴 기준 커밋이나 작업 시작 상태를 식별해 구현 뒤 대상 인수 테스트가 바뀌지 않았는지 대조할 수 있게 한다.
5. 실패한 요청의 호출 경로와 원인 코드를 확인한다. 코드의 설명은 가설이며 테스트와 실측 결과를 판정 기준으로 삼는다.
6. 같은 규칙이 적용될 가능성이 있는 유사 지점을 찾아 현재 티켓 범위인지 구분한다.

## 구현

- 실패 원인을 제거하는 최소 프로덕션 변경을 우선한다.
- 인수 테스트나 인수 조건을 약화해 통과시키지 않는다. 기준과 테스트가 어긋나면 구현을 진행하지 않고 대상 인수 테스트와 전체 테스트 결과를 미완료 근거로 남긴다.
- 기존 상태 코드, 오류 메시지, 저장 동작 등 현재 티켓과 무관한 행동을 보존한다.
- 유사 지점을 발견해도 현재 인수 조건의 적용 대상이 아니면 함께 고치지 않는다. 필요한 경우 후속 티켓 후보로 남긴다.
- 사용자 변경이 있는 작업 트리에서는 관련 없는 변경을 보존하고 요청 범위의 파일만 수정한다.

## 검증

1. 대상 인수 테스트를 실행해 Green을 확인한다.
2. 저장소가 지정한 전체 테스트를 실행해 회귀를 확인한다.
3. Red 기준과 대상 인수 테스트의 diff를 확인해 구현 과정에서 테스트나 인수 조건을 바꾸지 않았음을 검증한다.
4. 변경 파일과 diff를 검토해 테스트를 통과시키는 데 필요하지 않은 변경이 없는지 확인한다.
5. 저장소가 직접 실측을 요구하면 구현 전과 같은 경계를 다시 호출하고, 변경 전 기록과 구분해 남긴다.

대상 인수 테스트나 전체 테스트를 실행하지 못했거나 결과를 읽지 못한 경우에는 Green 또는 완료로 판정하지 않는다. 이전 실행 결과나 통과했다는 보고만으로 현재 상태를 대신 판정하지 않는다.

## 완료 보고

다음 내용을 반드시 포함한다. 파일 목록이나 diff 요약만으로 대신하지 않는다.

- **원인:** 기존 코드가 인수 조건과 어긋난 이유
- **변경:** 어느 지점을 어떻게 바꿨는지
- **범위:** 그 지점을 변경 대상으로 선택한 이유
- **범위 밖:** 확인한 유사 지점과 변경하지 않은 이유
- **검증:** 다음 판정 단계에서 독립 실행 결과와 대조할 수 있도록 대상 인수 테스트와 전체 테스트의 실행 명령, 통과·실패 및 확인 가능한 테스트 수, 필요한 실측 결과
- **테스트 보존:** Red 기준과 비교한 대상 인수 테스트의 변경 여부
- **남은 일:** 후속 티켓이나 추가 확인 사항

커밋, 푸시 등 별도 저장소 작업은 사용자가 명시적으로 요청했을 때만 수행한다.
