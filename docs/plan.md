# 작업 계획

티켓 하나를 처리하는 순서다. 지켜야 하는 것은 `principles.md`에 있다.

## 1. 인수 조건

- 입력: 티켓, 이 티켓에서 다룰 요구사항
- 하는 일: 코드에서 지금 동작을 파악하고, 요구사항과 어긋나는 자리를 판정한다
- 남기는 것: `acceptance-criteria.md`에 규칙과 예시와 이유. 못 정한 것은 질문으로, 남은 일은 `tickets.md`에
- 넘어가기 전에: 예시가 직접 호출해 받은 응답인지 확인한다
- AI에게 주는 지시
  - 요구사항이 침묵하는 자리(회색지대)를 만나면 acceptance-criteria.md에 질문으로 적고 티켓으로 등록한다. 무엇이 확인되면 이 티켓이 정리되는지를 함께 적는다(예: "운영 정책을 확인해야 정할 수 있다").
  - 인수 조건은 Given-When-Then 시나리오를 중심으로 쓰고 적용 범위, 이유, 경계별 판정, 남은 질문만 보탠다.
  - 직접 받은 응답은 상태 코드와 판정에 필요한 필드, 후속 조회값만 간결하게 옮긴다. 요청과 응답 전문은 붙이지 않는다.

## 2. 인수 테스트

- 입력: `acceptance-criteria.md`, `test-guide.md`
- 하는 일: 테스트 초안을 받아 규칙을 검증하는지 판정하고 실행한다
- 남기는 것: 테스트 코드와 직접 실행한 Red 결과, 구현 뒤 테스트 보존 여부를 대조할 수 있는 기준. 기준은 별도 커밋, 파일 해시 또는 작업 시작 상태로 남길 수 있으며 Red 전용 커밋은 필수가 아니다. 새 테스트 제약은 `test-guide.md`에 한 줄로 남긴다
- 넘어가기 전에: 현재 동작을 고정하는 회귀 테스트는 통과하고, 미구현 인수 조건 테스트만 실측과 일치하는 값으로 예상한 단언 위치에서 실패하는지 확인한다
- AI에게 주는 지시
  - 테스트 코드 작성 후 실패하는 케이스에 대한 코드 수정은 이 단계에서 하지 않는다

## 이 저장소의 실행 방법

- 서버 기동: `./gradlew bootRun`, 8080 포트. 8080이 쓰이면 `SERVER_PORT=8081 ./gradlew bootRun`
- 로그인은 `POST /auth/login`, 관리자 REST API는 `/admin`, 콘솔 화면 요청은 `/console` 아래에 있다.
- `POST /auth/login`에 관리자 계정으로 로그인해서 토큰을 받는다.
  - 이후 호출에는 이 토큰을 싣는다.
  - 계정은 README의 테스트 계정 표에 있다.
- 테스트 실행: `./gradlew test`. 결과 줄이 안 보이면 캐시다. `./gradlew test --rerun-tasks`로 다시 돌린다
- 데이터베이스는 인메모리 H2 `jdbc:h2:mem:testdb`이며, 상품은 `products` 테이블에 저장된다.
- 데이터를 다루기 전에 `src/main/resources/data.sql`을 읽는다.

테스트를 어떻게 짤지는 이 파일에 적지 않는다. 무엇을 단언하고 어떻게 격리할지는
작업하며 정해 `test-guide.md`에 쌓는다.
