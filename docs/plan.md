# 작업 계획

티켓 하나를 처리하는 순서다. 지켜야 하는 것은 `principles.md`에 있다.

## 1. 인수 조건

- 입력: 티켓, 이 티켓에서 다룰 요구사항
- 하는 일: 코드에서 지금 동작을 파악하고, 요구사항과 어긋나는 자리를 판정한다
- 남기는 것: `acceptance-criteria.md`에 규칙과 이유, 그리고 실제 호출 결과가 녹아든 Given·When·Then. 못 정한 것은 질문으로, 남은 일은 `tickets.md`에
- 넘어가기 전에: When·Then에 적은 결과가 직접 호출해 받은 응답인지 확인한다
- AI에게 주는 지시:
    - 규칙은 "무엇이 참이어야 하는가"로 쓴다. 특정 메서드·엔드포인트·구현 동작("~하면 거부한다", "createReservation은 ~검사한다")에 종속되게 쓰지 않는다. 도메인 참으로 쓰면 같은 규칙이 지켜져야 할 다른 경로(수정 등)가 문장만 보고도 드러난다.
    - 규칙/이유/Given·When·Then/질문 블록은 코드블록(```)으로 감싼다. 마크다운은 빈 줄 없는 연속된 줄을 한 문단으로 합쳐버리고, 트레일링 스페이스로 줄바꿈을 강제하는 방식은 린터가 지울 수 있다.
    - Given은 여러 케이스가 공유하는 전제 하나만 한 줄로 적는다. 케이스마다 달라지는 값은 Given이 아니라 각 When에 적는다.
    - When과 Then은 케이스 하나당 한 줄에 나란히 적는다: `When   <입력>    Then  <실제 호출로 받은 응답(HTTP 상태·핵심 메시지)>`. 별도의 "예시" 블록이나 "현재 상태" 문단을 덧붙이지 않는다 — 실제 응답 자체가 Then의 내용이다. 케이스가 여러 개면 같은 형식으로 When·Then 줄을 반복한다(경계값 등).
    - Then에 적는 응답은 직접 호출해 받은 실제 값이어야 한다(추측 금지). 날짜처럼 "오늘" 기준 상대값이 들어간 경우, 재검증 시점의 오늘 날짜로 다시 호출해 갱신한다. 오래된 "오늘" 기준 값을 그대로 남기지 않는다. 버그로 기대와 실제 응답이 다르면 Then에 실제 응답을 적고 괄호로 기대와 다르다는 것을 짧게 남긴다(예: `302, 조회 시 999로 나와야 하나 실제로는 20 그대로 (변경 안 됨)`). 이전에 버그였어도 그 사이 커밋된 수정이 있으면 다시 호출해 갱신한다 — 문서가 코드보다 뒤처진(stale) 채로 남지 않게 한다.
    - 요구사항이 침묵하는 자리(회색지대)를 만나면 Given·When·Then 아래 "질문"으로 남기고, 반드시 `tickets.md`에 짝이 되는 티켓을 같이 남긴다. 질문만 남기고 티켓을 빠뜨리지 않는다. 질문 자리의 버그 여부·사양 여부는 AI가 판정하지 않는다.
    - `tickets.md`에 이미 같은 내용이 티켓으로 있으면 `acceptance-criteria.md`에 산문으로 중복 설명을 남기지 않는다.
    - 규칙/이유는 tickets.md → acceptance-criteria.md 방향으로 만들어진다. acceptance-criteria.md에서 tickets.md 항목을 "참고"하라고 역참조하지 않는다(원천과 결과물의 방향이 바뀐다).
    - 이미 다른 티켓이나 acceptance-criteria.md 항목이 같은 내용을 다루면, 그 내용을 옮겨 적어 합치지 말고 중복 티켓 자체를 제거한다.

## 2. 인수 테스트

- 입력: `acceptance-criteria.md`, `test-guide.md`
- 하는 일: 테스트 초안을 받아 규칙을 검증하는지 판정하고 실행한다
- 남기는 것: 테스트 코드. 초안에 준 제약은 `test-guide.md`에 규칙 한 줄로
- 넘어가기 전에: 인수 테스트가 지금 실패하는지 확인한다. 실패하지 않으면 지금 동작을 겨눈 초안이다
- AI에게 주는 지시:
    - 버그 수정(구현)은 이 단계에서 하지 않는다.
    - 경계값은 별도 테스트 케이스로 분리한다.
    - 테스트에 쓸 시드 데이터는 추측하지 않고 직접 읽어 확인한 값을 쓴다.
    - 지금 코드로 실행하면 관련 테스트가 실패(레드)하는 것이 정상임을 명시한다.

## 3. 구현

- 입력: 실패하는 인수 테스트
- 하는 일: 그 테스트를 통과시키는 최소 변경
- 남기는 것: 코드
- 넘어가기 전에: `./gradlew test`로 인수 테스트가 지금 레드인지 직접 실행해 확인한다.
  `acceptance-criteria.md`의 Then 값을 근거로 레드라고 가정하지 않는다. 수정 후에는
  그 테스트가 통과하는지 확인한다
- AI에게 주는 지시:
    - 코드베이스의 레이어 관례를 따른다. 손대야 할 자리가 그 관례를 우회하고 있어도
      "기존 코드"라는 이유로 관례로 삼지 않는다. 같은 관심사를 다루는 관례적 위치가
      이미 있으면 그곳을 거치게 고친다(예: 트랜잭션 경계는 컨트롤러가 아닌 서비스에).

## 4. 판정

- 입력: 바뀐 코드, 쌓인 테스트 전부
- 하는 일: 이 티켓이 끝났는지 판정한다. 바뀐 코드를 읽고, 쌓인 테스트를 전부 돌려 회귀를 확인한다
- 남기는 것: 커밋. 처리하며 발견한 것이 있으면 `tickets.md`에
- 넘어가기 전에: 요구사항대로 됐고 원래 되던 것이 안 깨졌는지 확인한다
- AI에게 주는 지시:
    - 이번 티켓으로 그린이 된 인수 테스트의 `@Nested` Javadoc이 레드였던 시절 문구 그대로 남아 있지 않은지 확인하고, 남아 있으면 갱신한다(규칙은 `test-guide.md`).

## 이 저장소의 실행 방법

- 서버 기동: `./gradlew bootRun`, 8080 포트. 8080이 쓰이면 `SERVER_PORT=8081 ./gradlew bootRun`
- 호출할 수 있는 것은 `/api` 아래에 있다
- 테스트 실행: `./gradlew test`. 결과 줄이 안 보이면 캐시다. `./gradlew test --rerun-tasks`로 다시 돌린다
- 데이터를 다루기 전에 `src/main/resources/data.sql`을 읽는다

테스트를 어떻게 짤지는 이 파일에 적지 않는다. 무엇을 단언하고 어떻게 격리할지는
작업하며 정해 `test-guide.md`에 쌓는다.
