# 테스트 작성 제약

## 인수 테스트 클래스는 티켓 단위가 아니라 도메인 단위로 묶는다

- 규칙: 인수 테스트 클래스(또는 파일)는 티켓 번호가 아니라 도메인으로 이름 짓고, 여러 티켓의 테스트를 하나의 그룹(중첩 클래스/describe 블록 등, 언어·프레임워크에 맞는 그룹핑 단위)으로 함께 담는다. 최상위 주석에는 파일 전체에 공통되는 규칙만 남기고, 티켓 번호·왜 레드인지 같은 티켓별 세부 내용은 각 그룹 바로 위에 적는다.
- 이유: 최상위 주석에 티켓별 세부 내용을 적으면, 다음 티켓의 테스트가 같은 파일에 추가될 때 그 주석이 새 티켓 내용과 맞지 않게 된다.
- 적용: (프로젝트별 그룹핑 문법 — 예: JUnit @Nested, Jest describe, pytest 클래스 등)에 티켓 번호를 단 이름을 붙이고, 그 위 주석에 "왜 이 케이스가 지금 레드/그린인지"를 적는다.

## 격리는 우회하지 않고 명시적 초기화로 보장한다

- 규칙: 실제 서버/DB에 요청을 보내는 인수 테스트는 자동 롤백되지 않을 수 있다 — 커밋된 데이터가 그대로 남는다. 테스트 간 격리를 "먼 미래 값을 쓴다", "테스트마다 다른 식별자를 쓴다"는 식으로 우회하지 않고, 매 테스트 전 관련 데이터를 명시적으로 초기화해 보장한다.
- 이유: 값을 피해가는 방식은 테스트가 늘어날수록 어떤 값이 비어 있는지 계속 추적해야 해서 깨지기 쉽고, 재실행 시 이전 실행이 남긴 데이터와도 충돌할 수 있다. 명시적 초기화는 실행 순서·횟수와 무관하게 항상 같은 시작 상태를 보장한다.
- 적용: 이 프로젝트는 `@Sql` 스크립트로 초기화한다. 스크립트는 `src/test/resources/sql` 아래 도메인별 파일(예: `product-reset.sql`)로 두고, 초기화가 필요한 테스트 메서드에 `@Sql("/sql/{도메인}-reset.sql")`을 붙인다. 시드 데이터(`data.sql`)의 식별자를 그대로 재사용해도 되게 한다.

## 그룹 위 주석은 그 시점의 실제 레드/그린 상태를 설명해야 한다

- 규칙: 그룹 위 주석에 "왜 지금 레드/그린인지"를 적을 때는 그 시점의 실제 테스트 실행 결과와 일치해야 한다. 구현이 끝나 레드였던 케이스가 그린으로 바뀌면, "아직 구현되지 않아 실패하는 것이 정상이다" 같은 문장을 그대로 두지 않고 구현 완료 상태로 갱신한다.
- 이유: 주석이 실제 상태와 어긋나면, 나중에 이 테스트를 읽는 사람이 지금도 레드인 줄 알고 불필요하게 원인을 찾거나, 반대로 실제 레드인 케이스를 이미 해결된 것으로 착각할 수 있다.
- 적용: 언제 확인하는지는 각 프로젝트의 판정 단계 문서(예: plan.md)에 정한다.
