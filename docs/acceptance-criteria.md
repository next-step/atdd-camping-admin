# 인수 조건

## T-1 상품 수정 내용 저장

### 범위와 이유

- 대상은 `ProductAdminController.updateProduct`가 처리하는 `PUT /admin/products/{id}`다.
- 수정 응답에는 바뀐 값이 표시되지만 후속 조회에서는 이전 값이 나오는 증상이 있으므로, 응답이 아니라 별도 조회 결과로 저장 여부를 판정한다.
- 재고의 음수·누락·`null`·빈 값·공백·정수가 아닌 값은 T-3, 콘솔 수정과 REST의 재고 외 필드 영속화는 T-4에서 다룬다.

### 시나리오

#### 재고를 일반 양수로 수정

- Given 재고가 `20`, 이름이 `랜턴`, 가격이 `30000.00`, 상품 타입이 `RENTAL`인 상품이 있다.
- When 관리자 JWT로 재고를 `21`로 수정한다.
- Then HTTP 200 응답에 재고 `21`과 기존 이름·가격·상품 타입이 표시된다.
- And 별도 조회에서도 재고가 `21`이다.

#### 재고를 하한값 0으로 수정

- Given 재고가 `20`, 이름이 `랜턴`, 가격이 `30000.00`, 상품 타입이 `RENTAL`인 상품이 있다.
- When 관리자 JWT로 재고를 `0`으로 수정한다.
- Then HTTP 200 응답에 재고 `0`과 기존 이름·가격·상품 타입이 표시된다.
- And 별도 조회에서도 재고가 `0`이다.

#### 이름만 수정할 때 재고와 가격 보존

- Given 재고가 `20`, 가격이 `30000.00`인 상품이 있다.
- When 관리자 JWT로 이름만 수정한다.
- Then HTTP 200 응답과 별도 조회에서 재고는 `20`, 가격은 `30000.00`으로 유지된다.

### 변경 전 실측

- 실측일: 2026-08-29 (Asia/Seoul)
- `data.sql`의 상품 ID `1`과 `POST /auth/login`으로 받은 관리자 JWT를 사용했다.
- 각 수정 요청 뒤 별도의 `GET /admin/products`로 저장 상태를 확인했다.

| 경계 | 수정 응답 | 후속 조회 | 기대 결과 | 판정 |
|---|---|---|---|---|
| 재고 `21` | HTTP 200, 재고 `21` | 재고 `20` | 재고 `21` | 불일치 |
| 재고 `0` | HTTP 200, 재고 `0` | 재고 `20` | 재고 `0` | 불일치 |

## T-2 매출 리포트 금액이 화면마다 다름

### 범위와 이유

- 대상은 대시보드의 오늘 매출이 호출하는 `GET /admin/reports/revenue/daily`와 매출 화면의 요약 및 상세가 호출하는 `GET /admin/reports/revenue/range`, `GET /admin/reports/revenue/range/entries`다.
- 같은 거래는 어느 리포트에서 보더라도 같은 귀속일과 같은 금액으로 표시돼야 한다. 일별·기간 요약·상세 내역이 서로 다른 날짜 필드나 금액을 사용하면 안 된다.
- 판매와 대여는 거래가 발생한 `createdAt` 날짜에 귀속한다. 예약은 예약 거래를 나타내는 `reservationDate`에 귀속하며, 숙박 제공일인 `startDate`·`endDate`나 엔티티 생성 시각인 `createdAt`을 리포트별로 섞어 쓰지 않는다.
- 예약 귀속일을 `reservationDate`로 정한 이유는 대시보드의 오늘 예약과 일별·기간 매출 집계가 이미 이 필드를 예약 거래일로 사용하고, 체크인일은 거래가 아니라 서비스 시작일을 나타내기 때문이다.
- 서로 다른 기간의 화면 총액은 다를 수 있다. T-2는 화면 기본 기간을 같게 만드는 것이 아니라 같은 거래의 날짜와 금액을 모든 리포트에서 일치시키는 범위다.
- 예약·판매·대여의 절대 금액 산식은 T-5에서 확정한다. T-2에서는 현재 산식으로 계산된 한 거래의 금액이 리포트마다 달라지지 않는지만 다룬다.

### 시나리오

#### 예약 거래의 귀속일과 금액 일치

- Given 예약 #3의 예약일은 2026-08-04, 생성일은 2026-08-03, 체크인일은 2026-08-05이고 현재 산식의 예약 금액은 `50000`이다.
- When 관리자 JWT로 2026-08-04의 일별 매출, 하루짜리 기간 요약과 상세 내역을 조회한다.
- Then 세 응답은 HTTP 200이다.
- And 일별 매출과 기간 요약의 예약 매출은 모두 `50000`이다.
- And 상세 내역의 예약 #3도 귀속일이 2026-08-04이고 금액이 `50000`이다.

#### 예약 거래를 생성일이나 체크인일에 중복 귀속하지 않음

- Given 예약 #3의 귀속일이 2026-08-04로 정해져 있다.
- When 관리자 JWT로 생성일인 2026-08-03과 체크인일인 2026-08-05의 리포트를 조회한다.
- Then 두 날짜의 예약 매출과 상세 내역에는 예약 #3이 포함되지 않는다.

#### 같은 기간의 요약과 상세 금액 일치

- Given 2026-08-27부터 2026-09-02까지 예약·판매·대여 거래가 있다.
- When 관리자 JWT로 같은 기간의 매출 요약과 상세 내역을 조회한다.
- Then 상세 내역을 유형별로 더한 예약 `200000`, 판매 `40000.00`, 대여 `20000.00`이 요약의 각 금액과 같다.
- And 상세 내역 전체 합과 요약의 총 매출은 모두 `260000.00`이다.

### 구현 전 동작 실측

- 실측일: 2026-09-02 (Asia/Seoul)
- `data.sql`의 예약 #3을 사용하고, 날짜 필드가 우연히 같아서 결함을 가리지 않도록 생성 시각만 2026-08-03 12:00으로 바꿨다. 예약일 2026-08-04와 체크인일 2026-08-05는 유지했다.
- `POST /auth/login`으로 받은 관리자 인증 쿠키를 사용해 화면이 실제로 호출하는 API를 조회했다.
- 기간 합계와 판매·연결 대여는 `t2-revenue-fixture.sql`의 전용 거래를 실제 로그인으로 받은 Bearer 토큰과 함께 호출해 확인했다. 연결 예약일과 대여 생성일은 서로 다르게 두었다.

| 경계 | 조회일 | 직접 받은 결과 | 기대 결과 | 판정 |
|---|---|---|---|---|
| 일별 매출 | 2026-08-04 | HTTP 200, 예약 `50000` | 예약 `50000` | 일치 |
| 기간 요약 | 2026-08-04 하루 | HTTP 200, 예약 `50000` | 예약 `50000` | 일치 |
| 기간 상세 | 2026-08-04 하루 | HTTP 200, 예약 #3 금액 `50000`, 표시일 2026-08-03 | 예약 #3 금액 `50000`, 귀속일 2026-08-04 | 날짜 불일치 |
| 기간 상세 | 생성일 2026-08-03 하루 | HTTP 200, 예약 #3 없음 | 예약 #3 없음 | 일치 |
| 일별·기간 요약 | 체크인일 2026-08-05 하루 | HTTP 200, 예약 `0` | 예약 #3 미포함 | 일치 |
| 기간 요약·상세 | 2026-08-27~2026-09-02 | HTTP 200, 예약 `200000`, 판매 `40000`, 대여 `20000`, 전체 `260000`; 상세 유형별·전체 합도 동일 | 같은 기간의 요약과 상세 합계 일치 | 일치 |
| 판매 일별·기간 요약·상세 | 생성일 2026-08-29 | HTTP 200, 판매 `30000`, 상세 금액 `30000`, 표시일 2026-08-29 | 판매 생성일에 같은 금액으로 귀속 | 일치 |
| 연결 대여 일별·기간 요약·상세 | 생성일 2026-09-01 | HTTP 200, 대여 `20000`, 상세 금액 `20000`, 표시일 2026-09-01 | 대여 생성일에 같은 금액으로 귀속 | 일치 |
| 연결 대여 일별·기간 요약·상세 | 연결 예약일 2026-08-28 | HTTP 200, 대여 `0`, 상세 내역 없음 | 연결 예약일에 대여 미포함 | 일치 |

### 실측으로 확인한 가설

- 일별 매출과 기간 요약은 예약을 `reservationDate`로 필터링하고 `50000`으로 계산한다.
- 기간 상세도 예약을 `reservationDate`로 선택하고 금액은 `50000`으로 계산하지만, 응답의 `occurredAt`에는 `createdAt`을 넣는다.
- 그 결과 예약 #3은 8월 4일 상세에서 조회되면서 화면에는 8월 3일 거래로 표시되고, 정작 8월 3일 상세에는 나타나지 않는다. 같은 거래의 금액은 일치하지만 귀속일과 표시일이 다르다.

### 남은 질문

- `reservationDate`가 없는 예약을 매출에서 제외할지 다른 날짜로 대체할지는 T-5에서 확인한다.
- 예약 1박당 금액, 취소 예약 포함 여부와 대여 금액의 가격 시점 등 절대 금액 산식은 T-5에서 확인한다.
