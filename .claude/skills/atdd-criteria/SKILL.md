# 1. 인수 조건

`docs/principles.md`, `docs/plan.md`를 먼저 읽는다.

## 입력

- 인자로 받은 티켓 번호(예: T-3). `docs/tickets.md`에서 해당 티켓 내용을 찾는다.
- 이 티켓에서 다룰 요구사항. 호출 시 인자(예: `/atdd-criteria T-3 <추가 요구사항>`)로
  같이 받을 수 있다. 티켓 번호 뒤에 추가 텍스트가 있으면 그것을 이번 판정에서 반영할
  요구사항으로 취급한다. 없으면 `docs/tickets.md`에 적힌 내용만으로 판정한다.

## 하는 일

1. 관련 코드를 읽어 지금 동작을 실측으로 파악한다. 필요하면 서버를 띄워
   `/api` 엔드포인트를 직접 호출해 응답을 확인한다(추측 금지 — `principles.md`의
   "실측에 근거한 판정").
2. 요구사항과 코드의 지금 동작이 어긋나는 자리를 찾아 판정한다.
3. 요구사항이 침묵하는 자리(정할 수 없는 것)를 만나면 답을 만들지 않는다.

## 남기는 것

- `docs/acceptance-criteria.md`에 이 티켓의 규칙과 이유, 그리고 실제 호출 결과가 녹아든
  Given·When·Then. 못 정한 것은 그 아래 "질문"으로 적는다.
- 질문을 남겼으면 반드시 `docs/tickets.md`에 짝이 되는 티켓도 같이 추가한다. 질문만
  남기고 티켓을 빠뜨리지 않는다.
- 남은 일(추가로 발견한 결함, 별도 티켓감)은 `docs/tickets.md`에 추가한다.
- `docs/tickets.md`에 이미 같은 내용이 티켓으로 있으면 `acceptance-criteria.md`에 산문으로
  중복 설명을 남기지 않는다.

## AI에게 주는 지시

- 규칙은 "무엇이 참이어야 하는가"로 쓴다. 특정 메서드·엔드포인트·구현 동작
  ("~하면 거부한다", "createReservation은 ~검사한다")에 종속되게 쓰지 않는다. 도메인 참으로
  쓰면 같은 규칙이 지켜져야 할 다른 경로(수정 등)가 문장만 보고도 드러난다.
- 규칙/이유/Given·When·Then/질문 블록은 코드블록(```)으로 감싼다. 마크다운은 빈 줄 없는
  연속된 줄을 한 문단으로 합쳐버리고, 트레일링 스페이스로 줄바꿈을 강제하는 방식은
  린터가 지울 수 있다.
- Given은 여러 케이스가 공유하는 전제 하나만 한 줄로 적는다. 케이스마다 달라지는 값은
  Given이 아니라 각 When에 적는다.
- When과 Then은 케이스 하나당 한 줄에 나란히 적는다:
  `When   <입력>    Then  <실제 호출로 받은 응답(HTTP 상태·핵심 메시지)>`. 별도의 "예시"
  블록이나 "현재 상태" 문단을 덧붙이지 않는다 — 실제 응답 자체가 Then의 내용이다.
  케이스가 여러 개면 같은 형식으로 When·Then 줄을 반복한다(경계값 등).
- Then에 적는 응답은 직접 호출해 받은 실제 값이어야 한다(추측 금지). 날짜처럼 "오늘"
  기준 상대값이 들어간 경우, 재검증 시점의 오늘 날짜로 다시 호출해 갱신한다. 오래된
  "오늘" 기준 값을 그대로 남기지 않는다. 버그로 기대와 실제 응답이 다르면 Then에 실제
  응답을 적고 괄호로 기대와 다르다는 것을 짧게 남긴다(예: `302, 조회 시 999로 나와야
  하나 실제로는 20 그대로 (변경 안 됨)`). 이전에 버그였어도 그 사이 커밋된 수정이 있으면
  다시 호출해 갱신한다 — 문서가 코드보다 뒤처진(stale) 채로 남지 않게 한다.
- Then은 실제 호출로 "검증했다"는 근거이지, 응답을 옮겨 적는 자리가 아니다. HTTP
  상태와 판정에 필요한 핵심 값 하나(비교 대상 필드 값 하나 정도)만 짧게 적는다.
  응답 JSON 전체, 요청 바디 전체, curl 명령어, 여러 필드 나열은 옮기지 않는다 — 그 값이
  어디서 왔는지(무엇을 호출했는지)는 When에 이미 있으니 Then은 판정 결과만 짧게
  남긴다. T-1의 `302, 조회 시 "랜턴-수정됨"으로 나와야 하나 실제로는 "랜턴" 그대로
  (변경 안 됨)` 정도의 길이를 기준으로 삼는다.
- Given·When·Then은 사람이 읽는 도메인 언어로 쓴다. 실제 호출로 검증한 것과 문서에
  적는 표현은 다르다 — 검증은 실제 엔드포인트·파라미터·응답 필드로 하되, 문서에는
  그 결과를 도메인 언어로 옮겨 적는다. HTTP 메서드·경로·쿼리 파라미터(`GET
  /admin/reports/...?date=...`), 응답 JSON 필드명(`totalReservationRevenue`),
  코드 줄 번호·메서드명(`SalesService.java 146행`)을 Given·When·Then 문장에
  그대로 남기지 않는다. Then의 HTTP 상태 코드(예: `302`)는 예외로 남긴다 — 그 자체가
  판정 결과다. 원인이 되는 코드 위치는 Given·When·Then 블록이 아니라 그 아래
  설명 문단에 적는다. T-1의 `Given 상품(id=1)의 이름이 "랜턴"이다` 정도의 구체성을
  기준으로 삼는다.
- 요구사항이 침묵하는 자리(회색지대)를 만나면 Given·When·Then 아래 "질문"으로 남기고,
  반드시 `tickets.md`에 짝이 되는 티켓을 같이 남긴다. 질문만 남기고 티켓을 빠뜨리지
  않는다. 질문 자리의 버그 여부·사양 여부는 AI가 판정하지 않는다.
- `tickets.md`에 이미 같은 내용이 티켓으로 있으면 `acceptance-criteria.md`에 산문으로
  중복 설명을 남기지 않는다.
- 규칙/이유는 tickets.md → acceptance-criteria.md 방향으로 만들어진다.
  acceptance-criteria.md에서 tickets.md 항목을 "참고"하라고 역참조하지 않는다(원천과
  결과물의 방향이 바뀐다).
- 이미 다른 티켓이나 acceptance-criteria.md 항목이 같은 내용을 다루면, 그 내용을 옮겨
  적어 합치지 말고 중복 티켓 자체를 제거한다.
- 코드를 고치지 않는다. 이 단계는 판정만 한다.
- 이미 있는 티켓의 내용(제목·신고 문구)을 고치지 않는다. `tickets.md`는 원래 신고를
  그대로 담는 원천이라, 조사 후 알게 된 실제 원인·정정 사항은 그 티켓 내용을 다시
  쓰는 게 아니라 `acceptance-criteria.md`의 Given에 "제목/신고 문구를 그대로 믿지
  않는다" 식으로 남긴다. 새 티켓을 추가하는 것과는 다르다 — 새 티켓 추가는 계속
  한다.

## 통과 조건

When·Then에 적은 결과가 직접 호출해 받은 응답인지 확인한다. 통과하면 진행 여부를
사용자에게 묻지 않고 곧바로 `/atdd-test <티켓번호>`를 수행한다.
